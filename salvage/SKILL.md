# salvage — clear an older `thegraph` build out of a repo

An earlier `grill-the-graph` compiled repositories into a long document and
generated code from it: a build doc of several hundred lines, subagents, scripts,
an ignore line, a run-state cache. The current skill writes one short prose file
and generates nothing.

This removes the old one. **The whole job is telling two things apart** — what a
person sat down and answered, which has to survive, and what was copied out of
the repository, which is why the old build went. What survives does not all go to
the same place: some belongs in the new build, some in `CLAUDE.md`, some in a
decision record.

Leave nothing behind. A half-cleared repo is worse than an uncleared one: it has
a hook calling a script that no longer exists.

## How to find what is ours

**Three searches, and the third is the one that makes the list complete.** The
first two find what the build **wrote**; only the third finds what exists
**because** of it.

**① The build stamp.** Every generated file carried one — scripts as
`Generated by /grill-the-graph. Build stamp: <rev>`, agents as a
`**Build stamp: <rev>**` line. The old skill enforced this as a rule; it never
warned anyone that a file was stale, but it says exactly whose child a file is.

**② The build document's artifact manifest.** It lists what the build wrote.

**Cross-check those two.** A path in the manifest with nothing on disk was
already removed. **A stamped file the manifest does not name is the one that
matters** — the manifest is a copy, and this repo has measured that class of copy
going out of date on its own.

**③ Grep the whole tree for the paths ① and ② just gave you.** Every hit is one
of two things, and the difference is what it does with the path:

- it **calls** what you are removing — a hook, a CI step, a task runner
- it is **about** what you are removing — a document auditing the build slot by
  slot, an evaluation whose subject is the build, a check whose only corpus was
  the generated files

**The second kind carries no stamp**, so ① and ② are blind to it, and it is
exactly what a person wrote *because* the build existed. Measured in the one repo
that has done this: three hand-written check scripts (1,218 lines), a slot audit
(309), and three evaluations — **not one of them stamped, and not one of them
under either generated directory.** A cleanup that ran only ① and ② would have
left all seven.

**Do this before you show anything**, not after. A search that runs after the
deletion finds the same files and finds them too late to have been part of the
list somebody approved.

## The four rings

**Ring 1 — ours, delete it.** The table is **what to expect, not the list**; the
list is what ① and ② returned. A build that named its artifacts differently is
still that build's business, and the manifest is what knows.

| | |
|---|---|
| `docs/agents/thegraph.md` | the build document. Read for salvage first, then replaced |
| `.claude/agents/thegraph-*.md` | generated subagents |
| `scripts/thegraph/` | generated scripts |
| the ignore-file entry for the run-state directory | a line the old build added |
| the run-state directory itself | **ignored by version control, so `git status` never shows it.** Remove it from disk; a `git rm` will not |

**Ring 2 — someone else's file, pointing at ours. Delete the line, keep the
file.** Commit hooks, CI workflow steps, an agent-instruction file's trigger
line, a README row naming a generated artifact. These are the repo's own files
and call other things too, so **only the lines that name what ring 1 removed
come out.**

A repo left with a hook that invokes a deleted script cannot commit. Clearing
ring 1 and reporting ring 2 is not a cleanup, it is a break with a note attached.

**Ring 3 — our rules produced it, but we did not write it. Show it and ask.**
This is **whatever search ③ found that does not call anything** — a document
about the build rather than a caller of it. Do not go looking for the kinds
listed above; go looking for what the grep returned, because the kinds are one
repo's examples and the grep is the rule.

**And any ring-1 file a person edited after it was generated** — a later commit
touching a generated file makes it theirs, and deleting it would delete someone's
work. Ask; never assume.

**Outside — do not touch.**
Decision records, even ones whose links this breaks: a record describes the world
when it was written. Commit history. Anything carrying neither a stamp nor a
manifest entry.

## Process

### 1. Find

All three searches, in order: the stamp marker, the build document's manifest,
then the tree grepped for every path those two returned. Build the ring lists
from what came back rather than from the tables above. **Say which search found
each file**, and name anything the first two disagreed on — a stamped file the
manifest missed is the interesting one.

### 2. Sort ring 1 by who touched it last

For each generated file, ask git whether any commit after the one that added it
has touched it. If one has, move it to ring 3. This is cheap and it is the only
thing standing between a cleanup and deleting a person's edits.

### 3. Salvage the answers — three destinations, and only one is the build

**Into the new build**: the reference sources, how each is reached, which are
marked summarized, and the peer names a maintainer confirmed. The shape to write
them in is defined in
[`../grill-the-graph/SKILL.md`](../grill-the-graph/SKILL.md) — read it there
rather than reproducing it here.

**Two of that shape's columns the old document never had**, so they cannot be
lifted: what each source **informs** — how the thing works, or where files go —
and whether it **binds**, a spec that must be matched rather than an example that
may be diverged from. **Ask for both.** Guessing them is the same act as guessing
a sacred path, and a spec recorded as an example gets written up as a deliberate
difference and shipped.

**Into `CLAUDE.md`**: **the seams** — which surfaces are core, which reach the
core through a declared seam, what a consumer owns by definition. A repository
states its identity there or it states it nowhere, and that is where these are
read from now.

**Into the decision records**:

- **this project's tautological traps** — the checks that can only confirm what
  they assume. Each belongs in the record whose subject it is.
- **a written layout rule**, where the build carried one. `plat` authored it
  against a maintainer-confirmed peer set, and **no file in the repo restates
  it**; dropping it throws away work nobody can re-derive without running that
  comparison again.

**Dropped, and each drop gets a reason.** Two kinds, and say which:

- **The repository already answers it** — command lists, surface lists, record
  numbers, tracker capabilities, node rosters and counts, the manifest itself.
  A run reads these now.
- **Nobody could answer it** — the sacred-path list and the tie-breaker. A person
  ratified each, but the builder drafted it, which is what made it a copy rather
  than knowledge. The tie-breaker in particular was one sentence for a whole
  repository: a truism, or wrong case by case.

**The deliberate-divergence list is the one drop that is provably safe**, and say
so: every row carried the record that decided it, so the content is already in
the repo's decision records. Check that before dropping it, and where a row names
no record, put that row in front of the maintainer instead.

**When in doubt, it moves.** This skill exists because a person's answer is the
expensive half; the cost of carrying one extra line is a line, and the cost of
dropping one is that nobody knows it was ever answered.

### 4. One list, one approval

Show all of it on one screen: ring 1 and ring 2 to be removed, ring 3 to be
decided, and the salvaged file as it will be written. Ask once, with the tool
that renders a question.

**Not file by file.** Sequencing removals one at a time spends the reader's
attention on exactly the items already decided against; the salvaged file is the
part worth reading closely, and it is one page.

### 5. Remove, then write

Ring 1 and ring 2, then the salvaged build document in its place. Ring 3 only
where the answer said so.

### 6. Verify, and report what is left

**Re-run all three searches.** A cleanup that reports success without reading the
tree again has checked nothing. The third one is now a re-run rather than a first
look, and what it returns should be only what you deliberately left: a link
inside a decision record, a commit message, a historical note.

Report every remaining mention split into **fixed** and **left on purpose**. A
record describing the world when it was written is the second kind, and saying so
is what stops the next reader treating it as a miss.
